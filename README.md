### 🛠 Trouble Shooting: 인젝션 환경의 제약과 아키텍처 재설계

*   **v1.0 설계 및 데드락 발생:**
    타겟 프로세스 훅 내부에서 베이스 주소를 구하기 위해 `/proc/maps`를 읽으려 시도함. 초기에는 `fread`를 호출했으나 타겟 프로세스 흐름 정지로 인한 데드락 발생.

*   **v1.1 우회 시도 (시스템 콜 레벨 하강):**
    데드락을 피하기 위해 `open`, `read`로 전환. 하지만 인젝션 과정에서 타겟을 제어하기 위해 libc `read` 함수 초입에 `0xCC` (INT 3) 브레이크포인트를 삽입해 둔 상태였음. 훅 내부에서 `read`를 호출하자 이 브레이크포인트를 다시 건드리며 충돌 및 무한 루프(Recursion) 발생.

*   **v1.2 커널 직접 호출 적용:**
    조작된 libc `read`를 완전히 우회하기 위해 커널 시스템 콜(`syscall(SYS_read)`, `syscall(SYS_open)`)을 직접 호출하여 파일 I/O 충돌을 해결함.

*   **v1.3 훅 컨텍스트 스택 붕괴 방어 (`get_libc_sys`):**
    주소를 파싱하기 위해 할당한 큰 버퍼 공간(`0x4000`)으로 인해, 인젝션된 스레드의 제한된 스택이 오버플로우되며 크래시 발생. 스택을 보호하기 위해 해당 변수들을 `static`으로 선언하여 BSS(전역) 영역을 활용하도록 우회함.

*   **v2.0 아키텍처 한계 인식 및 재설계 (현재 진행):**
    시스템 콜로 I/O 충돌을 막고 BSS로 스택 붕괴는 막았으나, 훅 내부에서 주소를 동적으로 탐색하는 행위 자체가 치명적 한계임을 확인.
    
    1. 훅 내부에서 `strtok`, `sscanf` 등 libc 문자열 함수를 혼용하는 것 자체가 데드락을 유발하는 시한폭탄임.
    2. 스택 보호를 위해 선언한 `static` 변수는 단 1회의 Setup 과정에서만 사용하더라도, 멀티스레드 타겟 환경에서는 여러 스레드가 동시에 훅에 진입할 경우 BSS 영역을 덮어쓰는 레이스 컨디션(Race Condition)을 유발함. 동기화(Lock)를 걸면 다시 데드락 위험에 빠짐.
    
    결과적으로 외부 인젝터 구조로 전체 아키텍처를 이관하는 것이 맞으나, 이에 앞서 훅 엔진의 가장 핵심 로직인 **'Capstone 기반 명령어 분할(마일스톤 1.1)'** 및 **'RIP 상대 주소 보정 연산(마일스톤 1.2)'**의 안정성 검증이 최우선이라고 판단함.

    **[검증을 위한 통제 환경 구축 방안]**
    1. **타겟 환경 통제:** `target.c` 내부에서 전역 변수나 내부 함수를 호출하도록 수정하여, 도입부 14바이트 이내에 `[rip + offset]` 패턴의 명령어가 강제로 생성되도록 유도함.
    2. **동적 변수 배제:** 훅 내부의 불안정한 주소 탐색 로직(스캐닝 및 파싱)은 배제하고, 정적 분석으로 획득한 오프셋을 엔진에 **하드코딩(저격)**함.
    3. **코어 로직 고립 테스트 (TDD):** 환경적 불안정성을 0으로 만든 상태에서, 엔진이 14바이트를 정확히 자르고 오프셋을 정상적으로 재계산하여 크래시 없이 트램펄린을 생성하는지만을 독립적으로 검증할 예정임.
